## Independent specialist review and resolution

Requested independent read-only reviews from backend-engineer, frontend-engineer, ai-agent-engineer and security-engineer after the draft revision. Their findings were consolidated as follows:

- **Backend + frontend:** lifecycle/API roadmap mismatch, unspecified idempotency and cursor semantics, `202` versus execution model, terminal `reviewable`, incomplete response/event DTOs, and SQLite migration ambiguity. **Resolved:** Stage 1 uses bounded in-process work; `202` follows persisted queued state; restart marks unfinished runs interrupted; `reviewable` is terminal; cancellation is included and idempotent; same-key/same-request replays, changed request conflicts; cursor is exclusive; `investigations` owns atomic state/event sequence. SQLite is local disposable state, not migrated.
- **AI + backend:** verification needs a tamper-resistant oracle, same focused-test identity/hash, distinction among patch application and test failure, and explicit handling of flaky/non-comparable suite runs. **Resolved:** supervisor records process and provenance outside test process; exact focused test identity/hash is required; application classifies typed outcomes, not LLM; patch apply failure is distinct; non-repeatable or unavailable comparison is `inconclusive`. **Residual limitation:** hostile tests can manipulate reports; `verified_patch` is conditional evidence under a named policy, not proof correctness.
- **AI:** fake fixture-provider output could be confused with real model generation. **Resolved:** evidence includes producer origin/version and UI labels fixture/fake versus later provider/model.
- **Security:** local unauthenticated API requires browser/Host/loopback controls; fixture IDs need fixed-root resolution; local data needs owner-only storage; wheel hashes alone do not establish benign provenance; pytest config can request plugins despite autoload disable; network denial and runner gate need external enforcement/evidence. **Resolved:** same-origin proxy plus loopback, Host/Origin/Fetch Metadata/CSRF checks; manifest-root containment and no user paths; owner-private local data; provenance/review and isolated builder; runner-owned pytest config/fixed args/plugin checks; deny egress verified outside test process; default-off gate with no bypass and per-control evidence matrix.
- **Residual specialist disagreement/uncertainty:** exact local ACL implementation is platform-specific; pytest plugin restrictions cannot make `conftest.py`/tests safe; no test report proves correctness against malicious tests; the appropriate container-vs-VM boundary depends on deployment threat assessment. These remain security-stage evidence/selection items, not reasons to weaken the policy.

### Follow-up review of resolutions

The four specialists re-read the updated proposal. **Backend and frontend** confirmed that cursor, idempotency, cancellation, restart, polling, provenance, local proxy and SQLite choices were substantially aligned. They identified two remaining contract gaps: the response payload for evidence/proposals and cancellation-vs-completion race. **Resolved here:** detail responses enumerate evidence DTO fields and event envelope/types; CAS defines the race winner, late-result fence and caller response. Backend also requested atomic idempotency reservation; now explicitly required. Execution/verification statuses are separate; `simulated` is never a verification outcome; Stage 1 has no `latest_run` or retry endpoint.

**AI** confirmed Stage 1 consistency and identified verification-stage gates: oracle limitations, suite inventory identity, flaky-run repeat policy, numeric budgets and dynamic plugin registration. **Resolved where possible:** the architecture binds focused test identity/hash and suite-selection/inventory digest, states supervisor-vs-test-process trust boundaries, and makes changed/non-repeatable results inconclusive; dynamic plugin declarations are rejected. **Still unresolved and explicitly gated:** repeat counts/flake thresholds, trusted report parser/oracle details, suite inventory algorithm and numeric budget values.

**Security** confirmed the fail-closed stage order but requested a precise browser proxy trust contract, local file protections, wheel promotion controls, supervisor-channel isolation and race-resistant fixture opening. **Resolved in the proposal:** exact proxy/header/CSRF flow, per-OS app-data paths and owner-only permissions, no-follow fixture access, runner-only supervisor attestation channel, and explicit wheel provenance/promotion questions. **Residual gates:** verify ACL behavior on supported OSes; settle trusted wheel-source/build network/promotion criteria; validate network denial and runner isolation in the actual deployment environment.

No reviewer edited files or assessed runtime behavior. The remaining items are decisions before provider/runner/hosted enablement, not contradictions authorizing unsafe defaults.

### Stage 1 contract freeze clarifications

The contract incorporates the required queue admission ordering: reserve capacity before creating a new investigation; on saturation return `503 coordinator_capacity_exhausted` without consuming the idempotency key; commit the investigation, idempotency record and initial event atomically before enqueue; and recover a committed-but-not-enqueued unfinished row as `interrupted` after restart. Existing same-request idempotency replays and conflict behavior are preserved. The detail endpoint returns the original `report` without changing request validation limits. Stage 1 has no external-service contact at runtime; only developer setup may download BugPilot dependencies from an approved package source using a reviewed lockfile. These clarifications do not enable target dependency downloads, provider/GitHub calls, target code execution, or target pytest.
